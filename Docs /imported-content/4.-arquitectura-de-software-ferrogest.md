# 4. Arquitectura de software ferroGest

**Ana Lucia Bermudez Rodríguez - Aldair Caicedo Ramos - Samuel Cuervo Rojas - Kevin Andres Puentes Mera**

**Sistema de información web para la gestión de ventas e inventarios de ferreterías con asistente de IA**

Introducción

Este documento explica qué es la arquitectura de software, describe el patrón modelo vista controlador (MVC) y justifica por qué se utilizó en FerroGest, un sistema de información web para la gestión de ventas e inventario de una ferretería. Al final se muestra un ejemplo de cómo se aplicó con uno de los módulos del software.

La arquitectura de software\
La arquitectura de software de un sistema es la estructura, o conjunto de estructuras, del sistema. Comprende sus componentes, las propiedades de esos componentes que son visibles desde el exterior y las relaciones que hay entre ellos.\
La arquitectura no es el software en funcionamiento, sino una representación de este. Sirve para tres cosas: analizar si el diseño cumple los requisitos establecidos, considerar alternativas de organización en una etapa en la que todavía es fácil cambiar el diseño y reducir los riesgos asociados con la construcción del software.\
Para organizar los componentes se suelen emplear patrones de arquitectura, que son soluciones reconocidas y reutilizables a problemas de diseño frecuentes. Uno de los más usados en aplicaciones web es el patrón MVC.

El patrón MVC\
Definición\
MVC es un patrón de arquitectura de software que separa, mediante tres componentes, la lógica de la aplicación de la lógica de presentación. Se emplea desde componentes gráficos básicos hasta sistemas empresariales, y la mayoría de los frameworks modernos lo utilizan o usan una adaptación suya.\
Componente Qué hace\
Modelo: Representa los datos y las reglas del negocio, accede a la base de datos y desconoce cómo se muestra la información al usuario.\
Vista: Presenta la información al usuario y captura sus acciones como los clics o formularios, no contiene reglas del negocio.\
Controlador: Es el intermediario, recibe las acciones del usuario, las valida, pide al modelo que realice la operación y decide qué respuesta devolver a la vista.

Funcionamiento\
El usuario interactúa con la vista, esta envía la acción al controlador, el controlador solicita la operación al modelo, el modelo ejecuta la lógica y actualiza los datos, y el resultado regresa por el controlador hasta la vista, que se actualiza para mostrarlo.

¿Por qué usamos MVC?\
Separación de responsabilidades: La interfaz, las reglas del negocio y el acceso a datos quedan en capas distintas. Así, un cambio en una pantalla no obliga a modificar el cálculo del IVA ni las consultas a la base de datos.\
Trabajo en paralelo: El equipo fue de cuatro personas con roles distintos. Quien diseñó y programó las vistas avanzó sin esperar a quien programó los controladores y los modelos.\
Facilidad de pruebas: Las reglas del negocio viven en el modelo y se pueden probar sin necesidad de la interfaz. En FerroGest esto permitió ejecutar pruebas funcionales por módulo y por rol sin depender del navegador.\
Seguridad: Los controladores verifican el token de sesión, el rol del usuario y los datos recibidos antes de llegar al modelo, de modo que el control de acceso por rol quedó centralizado.\
Reutilización: Varias pantallas usan el mismo modelo. Por ejemplo, el dashboard y el asistente de IA consultan las mismas ventas y existencias a través del modelo, sin duplicar lógica.\
Coherencia: MVC encaja con el backend monolítico modular de FerroGest, que se organiza en rutas, controladores, servicios y modelos.

Cómo se aplicó

En FerroGest la interfaz está separada del servidor. La vista es la aplicación React que corre en el navegador, y el backend en Node.js implementa el controlador y el modelo. La vista y el controlador se comunican mediante peticiones HTTP/HTTPS con datos en formato JSON y el token de sesión en la cabecera `Authorization`. Es una adaptación habitual del patrón en aplicaciones web modernas. Capas del backend

&#x20;El backend se dividió en cuatro carpetas con una responsabilidad clara:

Capa Carpeta Responsabilidad&#x20;

Rutas `routes/` Definen las URL de la API y aplican los middlewares de sesión y de rol.

&#x20;Controladores `controllers/` Reciben la petición, validan los datos, eligen el código HTTP de respuesta y delegan el trabajo pesado.&#x20;

Servicios `services/` Concentran las operaciones con reglas de negocio y transacciones que afectan varias tablas: inventario y asistente de IA.&#x20;

Modelos `models/` Ejecutan las consultas SQL parametrizadas sobre MySQL.&#x20;

El middleware `verificarToken` consulta al usuario en cada petición y adjunta su rol; `permitirRoles` responde con 403 cuando el rol no está autorizado. De este modo, la seguridad no depende de que la interfaz oculte un botón. Cabe precisar que el nombre «modelo» del MVC no equivale a un ORM: en FerroGest los modelos son módulos de JavaScript que escriben el SQL directamente sobre la conexión de MySQL, sin una capa de abstracción adicional.&#x20;

Ejemplo

{% stepper %}
{% step %}
El vendedor completa el formulario&#x20;

El vendedor completa el formulario en la pantalla Registrar venta, que es la vista, y confirma.
{% endstep %}

{% step %}
La vista envía la petición

&#x20;La vista envía una petición `POST /api/ventas` con los datos en JSON y el token de sesión.
{% endstep %}

{% step %}
Las rutas y el controlador validan la solicitud&#x20;

La ruta aplica `verificarToken` y `permitirRoles('Administrador', 'Vendedor/Cajero')`. Después, el controlador valida el cliente, los productos, las cantidades, el medio de pago y el descuento, y responde con un error 400 si algo falta.
{% endstep %}

{% step %}
El controlador solicita la creación de la venta&#x20;

El controlador pide al modelo que cree la venta y delega en el servicio de inventario el ajuste de existencias.
{% endstep %}

{% step %}
El modelo y el servicio procesan la venta

&#x20;Dentro de una transacción de MySQL, el sistema calcula el siguiente número de ticket, verifica las existencias con bloqueo de fila (`FOR UPDATE`), calcula subtotal, descuento, IVA y total en centavos, guarda la venta y su detalle, descuenta el stock y registra un movimiento de inventario por cada producto.
{% endstep %}

{% step %}
Se confirma o revierte la transacción&#x20;

Si todo sale bien, confirma la transacción. Si algo falla, la revierte y no se guarda nada.
{% endstep %}

{% step %}
El controlador responde a la vista&#x20;

El controlador responde a la vista con el código 201 y los datos de la venta, o con el mensaje de error correspondiente.
{% endstep %}

{% step %}
La vista muestra el resultado

&#x20;La vista muestra la confirmación y la factura simulada en pantalla, con el número de comprobante, el detalle, el IVA y el total. El sistema no genera ni descarga un archivo PDF.
{% endstep %}
{% endstepper %}

Ventajas&#x20;

Cambios localizados: modificar una pantalla, una regla o una consulta afecta solo a su componente. Pruebas más sencillas de las reglas del negocio, sin depender de la interfaz.

&#x20;Trabajo en paralelo de los integrantes del equipo.&#x20;

Reutilización de la misma lógica en varias pantallas y en el asistente de IA.&#x20;

Conclusión El patrón MVC permitió organizar FerroGest en tres componentes con responsabilidades claras: la vista en React, y el controlador y el modelo en el backend de Node.js, con una capa de servicios para las operaciones que tocan varias tablas. Esta separación facilitó el trabajo en equipo, las pruebas y el mantenimiento, centralizó la seguridad en el middleware y los controladores y dejó las reglas del negocio en el modelo y en los servicios. Además, cumple el requisito de la asignatura y es coherente con la arquitectura monolítica modular elegida para el sistema.
