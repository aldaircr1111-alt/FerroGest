# 6. Arquitectura De Datos y Diseño De La Base De Datos En FerroGest

Ana Lucia Bermudez Rodríguez · Aldair Caicedo Ramos · Samuel Cuervo Rojas · Kevin Andres Puentes Mera

Sistema de información web para la gestión de ventas e inventarios de ferreterías con asistente de IA.

Introducción\
Este documento describe cómo se gestionan los datos en FerroGest y cómo se estructuró su base de datos. Primero se presentan los conceptos de arquitectura de datos y de diseño de bases de datos; después se describe la arquitectura de datos del sistema, incluyendo las necesidades de datos, flujo, volumen y seguridad; y, por último, se presenta el diseño de la base de datos MySQL, el modelo entidad-relación, el diccionario de datos y las decisiones de diseño.\
Conceptos\
Arquitectura de datos\
La arquitectura de datos describe cómo se gestionan los datos, desde su recopilación hasta su transformación, distribución y consumo, y establece cómo fluyen a través de los sistemas de almacenamiento. Sus metas son identificar los requerimientos de almacenamiento y procesamiento de datos, diseñar estructuras que respondan a las necesidades presentes y futuras, y preparar a la organización para evolucionar sus productos y servicios apoyándose en los datos.\
Diseño de base de datos\
El diseño de una base de datos representa su estructura, describe las entidades, sus relaciones y las restricciones entre ellas, para que se vea cómo se conectan. El proceso consiste en definir la estructura lógica y física de la base de datos para responder a las necesidades de información de los usuarios, decidiendo las tablas y relaciones, los atributos, y las claves primarias y foráneas de cada tabla.\
Lo primero en este proceso es la recogida y análisis de requisitos, que consiste en conocer en detalle las necesidades, expectativas y objetivos de los futuros usuarios de la base de datos. En nuestro software esa fase corresponde a la especificación de requisitos de software (ERS).

Flujo de datos

{% stepper %}
{% step %}
Recopilación Los usuarios ingresan los datos en los formularios de la interfaz React, es decir, productos, clientes, ventas, movimientos de inventario, etc.
{% endstep %}

{% step %}
Validación y transformación El backend verifica el token de sesión y el rol, valida los datos recibidos y los transforma cuando es necesario: calcula subtotal, descuento, IVA y total de una venta, y actualiza las existencias.
{% endstep %}

{% step %}
Almacenamiento Los datos se guardan en una base de datos relacional MySQL. Las operaciones que modifican varios registros, como una venta, se ejecutan como una sola transacción.
{% endstep %}

{% step %}
Distribución y consumo Los datos se consumen en las pantallas del sistema, en el dashboard, en la factura simulada y en las respuestas del asistente de IA. Para el asistente, el backend consulta primero los datos que el rol del usuario puede ver y solo entonces los envía al modelo de IA para que redacte la respuesta.
{% endstep %}
{% endstepper %}

Volumen de los datos Hasta 1.000 productos y 2.000 clientes registrados, y alrededor de 10 cuentas de usuario. Hasta 100 ventas diarias, es decir, hasta unas 36.000 ventas al año, cada una con varias líneas de detalle y sus movimientos de inventario. Hasta 3 usuarios conectados al mismo tiempo. Uso con predominio de consultas como búsquedas, listados y dashboard, y escritura moderada de ventas y movimientos de inventario. Seguridad Acceso por rol: Cada rol accede solo a los datos que le corresponden. El servidor vuelve a validar el rol en cada petición, sin confiar en lo que muestra la interfaz. Contraseñas y tokens: Las contraseñas se guardan como hash bcrypt. La tabla `token_recuperacion` está prevista para almacenar también el hash de los tokens de recuperación, con fecha de vencimiento, aunque su uso queda como mejora futura. Comunicación cifrada: En el entorno desplegado, los datos viajan entre el navegador y el servidor por HTTPS. Integridad: Las claves foráneas, las restricciones `CHECK` y las transacciones evitan datos inconsistentes, como existencias negativas o ventas sin detalle. Datos sensibles: El precio de compra solo se devuelve al administrador; a los demás roles se les excluye de la respuesta. Diseño de la base de datos Proceso de diseño

Vista `v_productos_stock_bajo`
Además de las nueve tablas, el esquema crea una vista que devuelve los productos activos cuya existencia es igual o inferior al stock mínimo, clasificados como `agotado` (existencia 0) o `bajo`. La usan el dashboard y el asistente de IA para no repetir la misma condición en varias consultas.
Decisiones de diseño
Eliminación lógica: usuarios, clientes y productos no se borran, se desactivan con el campo `activo`, para no romper el historial de ventas y movimientos.
Precio copiado en el detalle: `detalle_venta` guarda el precio y el IVA aplicados en el momento de la venta, de modo que un cambio posterior de precio no altere los comprobantes anteriores.
Kárdex completo: cada variación de existencias deja un registro en `movimiento_inventario` con la existencia resultante, lo que permite auditar cualquier diferencia.
Ventas anuladas, no borradas: la anulación cambia el estado, exige motivo y usuario, y genera movimientos de tipo `anulacion`.
Consecutivo del ticket: se obtiene con `MAX(numero) + 1` dentro de la misma transacción y con bloqueo de fila (`FOR UPDATE`), de modo que dos cajas no reciban el mismo número.
Importes en centavos: los campos `DECIMAL(12,2)` y el cálculo con dos decimales evitan los errores de redondeo de los tipos de punto flotante.
Consumidor Final: el cliente genérico con documento `222222222222` permite registrar ventas sin cliente identificado y no puede desactivarse.
Un solo script: `Database/schema.sql` crea la base, las tablas, los índices, la vista, los tres roles, el cliente genérico y las categorías iniciales.
Conclusión
La arquitectura de datos de FerroGest concentra toda la información en una base de datos MySQL a la que acceden únicamente el backend y, a través de él, la interfaz y el asistente de IA. El diseño se derivó de los requisitos de la ERS y quedó en nueve tablas con kárdex de inventario, eliminación lógica y transacciones que garantizan la consistencia de las ventas y las existencias. Además, la estructura deja espacio para crecer con las mejoras previstas sin rehacer lo existente.
