# 2. Especificacion de requisitos (IEEE830)

1. Introducción En esta sección se presenta una visión general de la Especificación de Requisitos de Software (ERS) del sistema de información FerroGest, elaborada siguiendo la estructura del estándar IEEE 830. Consta de las siguientes subsecciones: propósito, ámbito del sistema, definiciones, acrónimos y abreviaturas, referencias y visión general del documento.&#x20;
2. Propósito El propósito de este documento es especificar los requisitos funcionales y no funcionales del sistema FerroGest en su versión final implementada, una aplicación web para la gestión de ventas e inventario de una ferretería, que incluye un asistente conversacional con inteligencia artificial. Está dirigido al equipo de desarrollo y al docente de la asignatura como referencia formal del proyecto.&#x20;
3. Ámbito del sistema Nombre: El sistema se llamará FerroGest.&#x20;
4. Qué hará Gestionar usuarios y roles (administrador, vendedor y encargado de inventario), con control de acceso validado en el servidor; la interfaz oculta los módulos no autorizados y redirige al inicio del rol cuando se intenta abrir una ruta ajena. Administrar clientes, productos (con creación de categorías desde el formulario, definición de precios e IVA y stock inicial) e inventario (existencias y movimientos). Registrar ventas con valores en centavos, cálculo de totales, descuento automático de stock y generación de una factura simulada en pantalla. Mostrar un panel de indicadores (dashboard) adaptado por rol, con métricas del periodo por valor vendido, productos críticos y movimientos recientes. Incorporar un asistente conversacional con IA ubicado en el dashboard, limitado a seis consultas predefinidas y respetando los permisos de cada rol.&#x20;
5. Qué no hará FerroGest no incluirá contabilidad ni módulos financieros, nómina, compras a proveedores, facturación electrónica real ante la DIAN, pasarelas de pago ni tienda virtual para clientes. Tampoco incluye la recuperación de contraseña por correo electrónico: en esta versión, el restablecimiento lo realiza el administrador desde el módulo de Usuarios.
6. &#x20;Beneficios, objetivos y metas El sistema busca reducir errores de registro y faltantes de inventario, y dar mayor visibilidad del negocio para decidir. Su objetivo general es desarrollar un sistema de información web para la gestión de ventas de una ferretería que permita administrar clientes, productos, inventario y ventas, e incorpore un asistente conversacional con IA que responda consultas sobre la información del negocio, para mejorar el control operativo y la toma de decisiones.

30. &#x20;Restricciones El frontend se desarrolla en React, el backend en JavaScript con Node.js y los datos se almacenan en MySQL. El backend sigue el patrón Modelo Vista Controlador (MVC). El desarrollo sigue la metodología en cascada, con entregables documentales por fase. El equipo está conformado por cuatro personas con una dedicación aproximada de 10 horas semanales cada una, según el presupuesto. El asistente de IA depende de la API de un modelo externo, sujeta a su disponibilidad y a su costo por consulta. La facturación es simulada; no hay integración con la DIAN ni con pasarelas de pago. La comunicación entre el frontend y el backend se hace mediante una API HTTP/HTTPS con datos en formato JSON. El acceso está protegido por autenticación con token y las contraseñas se guardan con hash. El asistente de IA solo puede consultar mediante funciones predefinidas y no debe mostrar información fuera de los permisos del rol.&#x20;
31. Suposiciones y dependencias Los usuarios acceden a FerroGest desde un navegador web actualizado en cualquier sistema operativo. Los equipos de la ferretería tienen conexión estable a internet. Los requisitos descritos en este documento se mantuvieron estables durante la fase de implementación. Los datos iniciales del negocio son suministrados por el personal de la ferretería. El asistente de IA depende de la API de un modelo externo, por lo que se asume que seguirá disponible, con condiciones y costos por token similares a los actuales.

38. Requisitos específicos Esta sección contiene los requisitos de FerroGest con el nivel de detalle necesario para que se pueda diseñar, construir y probar el sistema. Cada requisito tiene un código único: los requisitos funcionales se identifican como RF-XXX-NN, por ejemplo, RF-VEN-01; y los no funcionales como RNF-XXX-NN, por ejemplo, RNF-SEG-01, donde XXX indica el módulo o categoría y NN el número consecutivo.&#x20;
39. Interfaces externas&#x20;
40. Interfaces de usuario La interfaz de usuario de FerroGest es una aplicación web que se ejecuta en el navegador, diseñada para pantallas de computador de escritorio y portátil. Toda la interfaz está en español y los valores monetarios se muestran en pesos colombianos. Todas las pantallas, excepto el inicio de sesión, comparten la misma estructura: Encabezado: ruta de navegación, nombre y rol del usuario autenticado, y botón para cerrar sesión. Menú lateral: muestra únicamente los módulos a los que el rol del usuario tiene acceso. Acceso al asistente de IA: botón flotante disponible en el dashboard, que abre un panel de chat lateral.
41. &#x20;Interfaces de hardware Se requiere un computador con capacidad para ejecutar un navegador web actualizado y conexión a internet. Para el mostrador se recomienda una resolución de 1600 × 900 y, si se usa, un lector de códigos de barras.
42. &#x20;Interfaces de software Navegador web actualizado: Chrome, Edge o Firefox. Backend desarrollado en Node.js: se conecta a una base de datos MySQL y consume la API de un modelo de IA externo mediante peticiones HTTPS.
43. &#x20;Interfaces de comunicación El servidor y el navegador se comunican mediante protocolos de internet estándares HTTP/HTTPS, los datos en formato JSON y el token enviado en cada petición.
44. &#x20;Funciones Los requisitos funcionales se organizan por módulo del sistema, lo que equivale a la organización por objetos que sugiere el estándar IEEE 830. Cada módulo corresponde a un conjunto de datos y funciones del negocio, coincide con la estructura del backend en MVC y con el reparto de trabajo del equipo. Los permisos por rol se resumen en la matriz del apéndice.&#x20;
45. 3.2.1 Autenticación RF-AUT-01 Iniciar sesión: El sistema permitirá a los usuarios iniciar sesión mediante correo electrónico y contraseña. Se asignará un token de sesión con una duración fija de 8 horas. RF-AUT-02 Cerrar sesión: El sistema permitirá al usuario cerrar sesión manualmente en cualquier momento; el cliente descarta el token y vuelve a la pantalla de inicio de sesión. RF-AUT-03 Restablecer contraseña: El administrador podrá asignar una contraseña nueva a cualquier usuario desde el módulo de Usuarios, sin necesidad de conocer la anterior.&#x20;
46. 3.2.2 Usuarios y roles RF-USR-01 Crear usuario: El sistema permitirá al administrador registrar nuevos usuarios asignando nombre, correo, contraseña inicial y rol (administrador, vendedor o encargado de inventario). RF-USR-02 Editar usuario: El sistema permitirá al administrador editar la información de los usuarios existentes (nombre, correo, rol y contraseña). El sistema impedirá que el administrador se quite a sí mismo su propio rol. RF-USR-03 Desactivar y reactivar usuarios: El sistema permitirá al administrador desactivar y reactivar usuarios con confirmación previa. No se permitirá que el administrador desactive su propia cuenta en uso. RF-USR-04 Consultar usuarios: El sistema permitirá al administrador consultar la lista paginada de usuarios registrados, incluyendo su rol, correo y estado actual. RF-USR-05 Control de acceso por rol: El servidor verificará el rol del usuario en cada petición HTTP y responderá con un error 403 cuando la operación no esté autorizada. La interfaz oculta los módulos no permitidos y redirige al inicio del rol si se intenta abrir una ruta ajena, sin exponer el contenido.
47. &#x20;3.2.3 Productos RF-PRO-01 Crear productos: El administrador y el encargado de inventario podrán registrar productos especificando código único, nombre, categoría —pudiendo crearse directamente desde el formulario—, unidad de medida, stock mínimo, precio de venta, porcentaje de IVA y stock inicial. Se permite la venta de productos con precio 0. RF-PRO-02 Editar productos: El administrador podrá modificar todos los datos del producto, incluido el precio de compra. El encargado de inventario podrá modificar los datos del producto, el precio de venta y el IVA, pero no el precio de compra. RF-PRO-03 Desactivar y reactivar productos: El sistema permitirá tanto al administrador como al encargado de inventario desactivar y reactivar productos sin eliminarlos del historial. RF-PRO-04 Consultar catálogo de productos: El sistema permitirá a todos los roles consultar el catálogo de productos con búsqueda por código o nombre. El vendedor no podrá visualizar el precio de compra.
48. &#x20;3.2.4 Inventario RF-INV-01 Consultar existencias: El sistema permitirá a todos los roles consultar las existencias de mercancía en tiempo real, destacando visualmente aquellos productos con stock igual o inferior al mínimo. RF-INV-02 Registrar entradas de inventario: El sistema permitirá al administrador y al encargado de inventario registrar entradas de mercancía sumando la cantidad al stock existente, con una nota opcional. La entrada se registra aunque el producto esté desactivado, para no perder el rastro de la mercancía recibida. RF-INV-03 Registrar ajustes por conteo físico: El sistema permitirá al administrador y al encargado de inventario registrar ajustes indicando la cantidad con signo y una nota obligatoria. El sistema no permitirá que las existencias resultantes queden en valores negativos. Nota: en esta versión el ajuste está disponible en la API; la pantalla de Inventario expone las entradas y el historial. RF-INV-04 Consultar historial de movimientos: El sistema permitirá al administrador y al encargado de inventario consultar el historial de movimientos de un producto con filtros por rango de fechas y tipo de movimiento. RF-INV-05 Alertar stock bajo: El sistema alertará en la interfaz y en el dashboard cuando un producto alcance un nivel de existencias igual o inferior a su stock mínimo definido.&#x20;
49. 3.2.5 Clientes RF-CLI-01 Registrar clientes: El sistema permitirá al vendedor y al administrador registrar clientes con su tipo, nombre o razón social, documento y teléfono. RF-CLI-02 Editar clientes: El sistema permitirá al vendedor y al administrador actualizar los datos de contacto e identificación de un cliente registrado. RF-CLI-03 Consultar y buscar clientes: El sistema permitirá al vendedor y al administrador buscar y consultar el listado paginado de clientes. RF-CLI-04 Consultar historial de compras de cliente: El sistema permitirá únicamente al administrador consultar el historial de compras de un cliente y su total acumulado. RF-CLI-05 Desactivar y reactivar clientes: El sistema permitirá al administrador desactivar y reactivar clientes. El cliente predefinido «Consumidor Final» no podrá modificarse ni desactivarse.&#x20;
50. 3.2.6 Ventas RF-VEN-01 Registrar venta: El sistema permitirá al vendedor y al administrador registrar una venta seleccionando un cliente y uno o más productos. El sistema descontará automáticamente el stock sin permitir existencias negativas. RF-VEN-02 Calcular totales de venta: El sistema calculará automáticamente el subtotal, el descuento proporcional y el IVA por producto. Todos los importes monetarios se calcularán y almacenarán con dos decimales (centavos), sin redondeo al peso. RF-VEN-03 Descontar stock: El sistema descontará automáticamente el stock al confirmar la transacción, registrando el movimiento correspondiente del tipo venta. RF-VEN-04 Generar factura simulada en pantalla: El sistema mostrará una factura simulada en pantalla tras la confirmación de la venta, con el número de comprobante; no dispondrá de descarga en archivo PDF. RF-VEN-05 Consultar historial de ventas: El sistema permitirá consultar el historial de ventas registradas. El administrador visualizará la totalidad de las ventas y el vendedor únicamente las suyas. RF-VEN-06 Anular venta: El sistema permitirá al administrador anular una venta registrada previa confirmación e indicando el motivo, reincorporando automáticamente las cantidades al inventario.&#x20;
51. 3.2.7 Dashboard RF-DAS-01 Mostrar indicadores de ventas: El sistema desplegará el valor total acumulado de las ventas realizadas en el día y en el mes actual. RF-DAS-02 Mostrar el resumen del periodo seleccionado: El sistema permitirá elegir entre hoy, esta semana y este mes, y recalculará con ese filtro el total vendido, el ticket promedio y el Top 5 de productos. RF-DAS-03 Mostrar productos más vendidos y stock bajo: El sistema desplegará los 5 productos más vendidos del periodo seleccionable, calculados en función del valor total vendido, y el listado de productos en estado crítico de inventario. RF-DAS-04 Adaptar dashboard al rol: El sistema adaptará la vista del dashboard según el rol: el administrador verá totales globales; el vendedor visualizará solo sus ventas; el encargado de inventario observará los últimos 10 movimientos de inventario y 8 productos críticos, sin métricas de ventas.&#x20;
52. 3.2.8 Asistente de IA RF-IA-01 Recibir consultas en lenguaje natural: El sistema incluirá el panel de chat con la IA dentro de la pantalla del Dashboard, accesible desde un botón flotante. RF-IA-02 Responder consultas predefinidas con datos reales: El asistente responderá a seis tipos de consultas predefinidas, ejecutadas como funciones en el servidor y no como SQL libre: existencias y precios de un producto, productos con stock bajo o agotados, ventas por periodo, productos más vendidos, historial de compras de un cliente y ventas por vendedor. El modelo de IA solo redacta la respuesta a partir de los datos que recibe. RF-IA-03 Respetar permisos de rol en el asistente: El asistente limitará sus respuestas y los datos entregados según los permisos del rol. El administrador accede a las seis consultas; el vendedor y el encargado solo a existencias, precios y stock bajo. Las funciones restringidas se excluyen antes de llamar al modelo y el servidor vuelve a validar el rol al ejecutarlas. RF-IA-04 Manejar consultas no soportadas y fallos de servicio: El asistente informará al usuario cuando una consulta no corresponda a los tipos soportados o cuando el servicio de IA no esté disponible, sin bloquear el resto del sistema. RF-IA-05 Limitar el uso del asistente: El sistema admitirá preguntas de hasta 500 caracteres, un máximo de 15 consultas por minuto por usuario y un tiempo de espera de 30 segundos por respuesta.&#x20;
53. Requisitos de rendimiento FerroGest está pensado para una ferretería pequeña. La carga y el volumen de datos estimados son: El sistema deberá responder en menos de 5 segundos a las operaciones habituales con la carga estimada. El asistente deberá entregar su respuesta en un máximo de 30 segundos, dado que depende de un servicio externo. El sistema deberá permitir que hasta 3 usuarios operen a la vez sin que se pierdan ni se dupliquen registros.&#x20;
54. Restricciones de diseño La arquitectura del backend sigue el patrón MVC; la interfaz se implementa en React como capa de vista independiente que consume la API del backend. Los datos se almacenan en una base de datos relacional MySQL, con transacciones para las operaciones que modifican varios registros. La comunicación entre el frontend y el backend se hace mediante una API sobre HTTP/HTTPS con datos en formato JSON. El asistente de IA accede a los datos del negocio únicamente mediante funciones predefinidas del backend y no puede ejecutar consultas libres sobre la base de datos. Los productos, clientes y usuarios no se eliminan; se desactivan, para conservar la integridad del historial.&#x20;
55. Atributos del sistema
56. &#x20;Seguridad
57. &#x20;RNF-SEG-01 Contraseñas: Las contraseñas deberán tener mínimo 8 caracteres y almacenarse únicamente como hash bcrypt, nunca en texto plano.&#x20;
58. RNF-SEG-02 Sesión: La sesión se identificará mediante un token JWT que se envía en cada petición y que expira 8 horas después de iniciada, sin renovación automática.&#x20;
59. RNF-SEG-03 Control de acceso: El servidor deberá verificar el rol del usuario en cada petición y rechazar con 403 las que no estén permitidas.
60. &#x20;RNF-SEG-04 Comunicación cifrada: En el entorno desplegado, toda la comunicación entre el navegador y el servidor deberá realizarse mediante HTTPS.&#x20;
61. RNF-SEG-05 Clave de la API de IA: La clave de acceso a la API del modelo de IA deberá guardarse solo en el servidor, en las variables de entorno, y no deberá ser visible en el navegador ni en el repositorio de código.&#x20;
62. RNF-SEG-06 Validación de datos: El servidor deberá validar los datos recibidos y usar consultas parametrizadas para prevenir la inyección SQL.&#x20;
63. RNF-SEG-07 Revocación inmediata: El servidor deberá consultar el estado y el rol del usuario en cada petición, de modo que una desactivación o un cambio de rol surtan efecto de inmediato, aunque el token siga vigente.
64. &#x20;Usabilidad&#x20;
65. RNF-USA-01 Idioma y formato: Toda la interfaz deberá estar en español y mostrar los valores monetarios en pesos colombianos con separador de miles.
66. &#x20;RNF-USA-02 Consistencia: Todas las pantallas compartirán la misma estructura de navegación, los mismos mensajes de confirmación y los mismos patrones de formulario.
67. &#x20;RNF-USA-03 Mensajes: Los errores deberán explicar qué corregir, sin exponer detalles técnicos ni indicar cuál de los dos datos de acceso falló.
68. &#x20;Fiabilidad y disponibilidad&#x20;
69. RNF-FIA-01 Integridad transaccional: Una venta, su detalle y los movimientos de inventario deberán guardarse en una sola transacción; si una parte falla, no se guardará ninguna.&#x20;
70. RNF-FIA-02 Concurrencia: El sistema deberá bloquear el producto durante la venta para que dos cajas no vendan las mismas unidades.&#x20;
71. RNF-FIA-03 Degradación: Si el servicio de IA no responde, el resto de los módulos deberá seguir operando con normalidad.&#x20;
72. Mantenibilidad&#x20;
73. RNF-MAN-01 Organización: El backend se organizará en rutas, controladores, servicios y modelos, con una responsabilidad clara por archivo.
74. &#x20;RNF-MAN-02 Documentación: El repositorio deberá mantener el README, la ERS y el manual de usuario actualizados con cada cambio funcional.&#x20;
75. RNF-MAN-03 Configuración: Las credenciales y parámetros de conexión se leerán de variables de entorno, no del código.&#x20;
76. Portabilidad y compatibilidad&#x20;
77. RNF-POR-01 Navegadores: La aplicación deberá funcionar en las versiones actuales de Chrome, Edge y Firefox.&#x20;
78. RNF-POR-02 Resolución: La interfaz deberá ser usable en pantallas de 1366 × 768 en adelante, con un diseño optimizado para 1600 × 900.&#x20;
79. RNF-POR-03 Base de datos: El esquema deberá poder crearse en MySQL 8.0.16 o superior ejecutando un único script.
