Introducción y Alcance del Sistema&#x20;

El presente documento describe los patrones de diseño, tanto de interfaz (UI) como de arquitectura de software, que se aplicaron en el desarrollo del sistema de información de la ferretería. El proyecto funcionó como una aplicación web centralizada, construida con una arquitectura en capas y componentes reutilizables. Para cumplir con los requerimientos del proyecto, se definió el siguiente stack tecnológico:&#x20;

Frontend: React, organizado mediante componentes reutilizables.

&#x20;Backend: Node.js con JavaScript, creando una API REST para procesar la lógica de negocio.

&#x20;Base de Datos: MySQL para el almacenamiento relacional de inventarios, usuarios y transacciones. Cabe aclarar que algunos elementos previstos en el mockup de Figma no llegaron a la versión implementada. Donde ocurre, este informe describe lo que realmente quedó en el sistema y lo señala de forma explícita.&#x20;

Patrones de Diseño de Interfaz de Usuario (UI Design Patterns) Aplicados Durante la construcción de las pantallas se aplicaron los siguientes patrones de interfaz:&#x20;

App Shell con barra lateral persistente: Todas las pantallas autenticadas comparten la misma estructura: una barra lateral fija con la marca y el menú, y un encabezado superior con la ruta actual, el nombre y el rol del usuario y el botón de cerrar sesión. El menú se agrupa en dos secciones, Operaciones y Configuración, y solo muestra los módulos permitidos para el rol, de modo que el usuario cambia de sección en un clic sin perder la ubicación.&#x20;

Patrón de Tarjetas de Indicadores Clave / KPI Summary Cards: Aplicado en la parte superior del dashboard, con tarjetas que resumen el periodo seleccionado: ventas del día y del mes, stock bajo y crítico, total vendido, ticket promedio, comprobantes anulados y reparto entre efectivo y medios digitales. El encargado de inventario ve tarjetas equivalentes de stock, productos agotados, artículos activos, desactivados y unidades ingresadas.&#x20;

Patrón de Búsqueda Dinámica y Filtrado Combinado / Search & Filter Pattern: Aplicado en la barra de búsqueda de Inventario (por SKU, código de barras o nombre) combinada con el selector de categoría y los filtros de estado; y en Ventas, con búsqueda por código o nombre y botones de categoría. También se usa en Clientes (nombre, razón social o documento) e Historial de Ventas (número, estado, medio de pago y fechas).&#x20;

Patrón de Tabla de Datos Paginada con Alertas Visuales / Paginated Data Grid & Status Highlighting: Aplicado en la tabla de productos de Inventario, que muestra código, nombre, categoría, existencias y precios, con paginación inferior y resaltado en rojo o ámbar cuando la existencia es crítica o está agotada. El mismo patrón se repite en Clientes, Usuarios e Historial de Ventas.&#x20;

Patrón Maestro-Detalle / Master-Detail: Implementado en el módulo de Ventas: el catálogo del mostrador ocupa el área principal y el panel lateral derecho desglosa la compra activa, con cantidades, descuento, subtotal, IVA, total, medio de pago y monto recibido. En Clientes, el listado abre un panel de detalle que incluye el historial de compras cuando el usuario es administrador. Patrón de Contenedores y Tarjetas / Card Layout: Utilizado para estructurar los formularios de autenticación, los modales de alta y edición, y los bloques de analítica del dashboard, separando visualmente la información operativa del resto de la interfaz.&#x20;

Patrón de Asistente Flotante / Floating Assistant: El asistente de IA se abre desde un botón flotante ubicado en la esquina inferior derecha del dashboard. Al pulsarlo aparece un panel de chat lateral que no interrumpe la pantalla y se cierra con un botón.

&#x20;Patrón de Confirmación para Acciones Destructivas: Las operaciones sensibles, como anular una venta o desactivar un usuario, producto o cliente, exigen un paso de confirmación con un motivo o una advertencia previa, en lugar de ejecutarse con un solo clic.

> Patrones a Nivel de Arquitectura del Software
>
> &#x20;Por debajo de la interfaz, el sistema implementa una estructura lógica para conectar las tecnologías elegidas:&#x20;
>
> Arquitectura Cliente-Servidor: React corre en el navegador del cliente (la computadora de la ferretería o la caja registradora) y se comunica mediante peticiones HTTP con la API REST del servidor en Node.js y Express. El servidor es el único que conoce la base de datos y las credenciales.&#x20;
>
> Patrón de Capas / Layered Pattern: El backend separa rutas (definición de URL y middlewares), controladores (validación, códigos HTTP y orquestación), servicios (reglas de negocio y transacciones que afectan varias tablas, como inventario y asistente) y modelos (SQL parametrizado). Ninguna capa salta a otra: una ruta no consulta la base directamente. Modelo-Vista-Controlador (MVC): React actúa como vista, los controladores como intermediarios y los modelos como acceso a datos y reglas del negocio. El detalle se desarrolla en el documento 4. Arquitectura de software.&#x20;
>
> Middleware en cadena / Chain of Responsibility: Cada petición atraviesa `verificarToken`, que valida el JWT y consulta al usuario en la base, y luego `permitirRoles`, que responde con 403 si el rol no corresponde. El encadenamiento permite reutilizar ambos controles en todas las rutas sin repetir código.&#x20;
>
> Fachada de servicios / Service Layer: La lógica de inventario se concentra en `services/inventario.service.js`, que expone operaciones como registrar movimiento y ajustar existencias y administra la transacción completa. Los controladores de ventas y movimientos usan esa fachada en lugar de replicar el cálculo del stock.&#x20;
>
> Pool de conexiones / Object Pool: La aplicación abre un grupo de hasta diez conexiones reutilizables a MySQL (`mysql2/promise`), en vez de abrir y cerrar una conexión por petición.&#x20;
>
> Objeto de transferencia de salida / DTO: Antes de responder, los controladores adaptan la fila de la base al rol del usuario. Por ejemplo, `prepararProducto` elimina el precio de compra cuando quien consulta no es administrador.&#x20;
>
> Transacción / Unit of Work: La venta, su detalle, el descuento de existencias y los movimientos de inventario se confirman o se revierten como una sola unidad. El bloqueo `SELECT … FOR UPDATE` evita que dos cajas vendan las mismas unidades.&#x20;
>
> Componentes contenedores y de presentación: En React, las páginas (`pages/`) cargan los datos y manejan el estado, mientras los componentes de `components/` reciben propiedades y solo pintan. Esto facilitó reutilizar las mismas tarjetas en las tres vistas del dashboard.&#x20;
>
> Contexto y hooks personalizados: `AuthContext` guarda la sesión y el rol en un solo lugar; `useTicket` y `useChat` encapsulan la lógica del punto de venta y del asistente para que las pantallas queden más simples.
>
> &#x20;Componente guardián / Protected Route: `RutaProtegida` envuelve las rutas privadas: si no hay sesión redirige al login y, si el rol no tiene acceso, redirige al inicio del rol. Es una ayuda de navegación; la autorización real la hace el servidor.
>
> &#x20;Consultas predefinidas para el asistente / Tool Use: El asistente no recibe la base de datos ni puede escribir SQL. El modelo elige entre seis funciones de solo lectura registradas en el servidor, y el backend ejecuta la consulta, filtra por rol y devuelve los datos para que el modelo redacte la respuesta.
>
> Conclusión\
> La combinación de patrones de interfaz —barra lateral persistente, tarjetas de indicadores, búsqueda combinada, tablas paginadas con alertas y maestro-detalle— hace que el sistema sea reconocible y rápido de operar para el personal de la ferretería, incluso sin capacitación extensa.\
> En el backend, la arquitectura cliente-servidor con capas, middleware en cadena, fachada de servicios y transacciones mantiene el código ordenado, centraliza la seguridad y garantiza que el inventario y las ventas nunca queden en un estado inconsistente. La diferencia entre el mockup y el producto final se documentó de forma explícita para que la entrega refleje lo que realmente se construyó.\
